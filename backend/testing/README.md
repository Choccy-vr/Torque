# API test harness

A single page for signing in with the real OIDC provider and firing authenticated
requests at the backend. Served by the backend itself (Development only), so
everything is same-origin and no CORS config is involved.

## Run it

```bash
./backend/testing/run.sh
```

Then open <http://localhost:5267/testing/>.

The script starts Supabase if it is down, copies the `@supabase/supabase-js` browser
bundle into `vendor/`, checks `backend/.env`, and runs the backend.

## Config

Nothing is hardcoded in the page. It fetches `/testing/config`, which returns three
values read from `backend/.env`:

| Key | Purpose |
|---|---|
| `SUPABASE_URL` | Which Supabase instance to talk to |
| `SUPABASE_ANON_KEY` | Public client key — `supabase status` prints it |
| `TESTING_OIDC_PROVIDER` | Provider identifier passed to `signInWithOAuth`, e.g. `custom:hackclub-auth` |

`/testing/*` is only mapped when `ASPNETCORE_ENVIRONMENT=Development`, so none of
this exists in a production build.

## Adding an endpoint

Append to the `ENDPOINTS` array at the top of `app.js`:

```js
{
  id: 'devlog-create',              // unique, used for element ids
  method: 'POST',
  path: '/api/devlog/{projectId}',  // {name} placeholders become inputs
  auth: true,                       // pre-ticks the auth box
  desc: 'Shown under the row.',
  params: [{ name: 'projectId', placeholder: 'project uuid' }],
  body: { text: 'hello' },          // prefills the JSON body editor
}
```

The "Custom request" panel handles anything not worth adding permanently.

## Notes

- Sign-in redirects back here, so the harness URL must be in `additional_redirect_urls`
  in `supabase/config.toml`. `http://localhost:5267/testing/**` is already listed.
- `GET /api/user/me` returns **404** for a freshly signed-in user: nothing provisions a
  row in `public.users` on sign-in yet. The response panel detects this and offers a
  seed `insert` statement filled in with your real `sub` and OIDC claims.
- `vendor/` is generated by `run.sh` and gitignored.
